## 0. Правила работ

1. Сначала восстановить доверие к **картам и героям**. Нельзя лечить потерю карт увеличением Груза или новой кнопкой.
2. Каждый небольшой пакет: воспроизведение → решение/контракт → код → автоматический тест → игровой сценарий →
   короткая запись «что изменено и что ещё неизвестно». Не объявлять весь мод исправленным после одного зелёного job.
3. Не менять одновременно ресурсы, пулы, наборы карт, сложность боссов и UI. Иначе плейтест не объяснит причину результата.
4. Публичные ID моделей и сохранённые свойства без миграции не переименовывать. Перед миграцией — копия сейва.
5. Стабилизационные исправления отделять от согласования нового дизайна. Новые правила требуют решения автора.
6. Планы, прототипы, автоматические прогоны и игровая приёмка — разные статусы. Число прогонов не является качеством модели.
7. Этапы ниже — порядок зависимостей, **не обещание закончить весь объём за одну ночь**. Календарные оценки появятся
   после первых двух пакетов и реального времени приёмки; арт/анимации могут потребовать отдельных исполнителей.

### S1. Сохранность карт, предметов и оплаты

**Блокеры:** N-02…06. Пакеты делать небольшими, каждый с собственным воспроизведением.

#### S1.1 Полка Кличей

- Согласовать владение боевой картой вне стопки и идентичность боя.
- Восстановление не проверять через `card.CombatState` снятой карты; не дублировать регистрацию/экземпляр.
- Возвращать/удалять запись полки только в соответствии с результатом.
- Проверить все Кличи, полную руку, занятую полку, повторы, перенаправление, конец боя и кооп.

#### S1.2 Общий контракт Add/Replace/Transfer

- Инвентаризация **всех** `CardPileCmd.Add/AddGeneratedCardToCombat`, замен колоды и `RelicCmd.Obtain/Replace`.
- Причины операции: награда/покупка/обязательная прогрессия/возврат/замена/навязанная карта.
- Явный результат `success/declined/deferred/failed`, а не `Task` без проверки и не всегда `true`.
- Preflight для UI полезен, но не заменяет commit-проверку: состояние может измениться во время выбора.
- Решить поведение при отказе: откат, сохранение источника или безопасный inbox. Операции не должны терять источник
  до выдачи результата; частичные изменения и сетевые повторы нужно учитывать отдельно.

#### S1.3 Сундук и ремонт сохранений

- Полные сериализованные свойства вещей/карт вместо class names; новая версия формата.
- Миграция старого содержимого без попытки выдумать утраченные чары/заточку; исходный backup и понятный отчёт.
- Пакетный перенос, дубликаты одного типа, исключение на середине, прежний loadout после возврата.
- Восстановление недостающих обязательных карт форм/Путей по сохранённому источнику, строго без дублей.
  Если старый save уже потерял данные и не содержит источника/истории, использовать original backup/явный отказ,
  а не угадывать выдачу по отсутствию карты такого класса.

#### S1.4 Платные услуги

- Переписывание: карта принята → свиток и цена committed; при отказе весь исходный набор сохранён.
- Тем же контрактом проверить варку/перековку/зачарование/заказы, а не чинить только единственный найденный пример.
- Убрать ложную подсказку «снимите снаряжение», если имеется в виду backpack: он продолжает весить. Нужен сундук/продажа/
  допустимое удаление или изменение самого правила, но не неправильная инструкция.

**Выход:** `CARD-01…12`, `STORE-01…09`, `SHOP-01…03`; по каждому сценарию есть тест отказа и тест успеха.
Ни одна обязательная карта не теряется; число/свойства объектов и оплата сохраняются при неуспехе.

### S3. Создание героя, стартовый бонус, владение и Перерождение

**Связь:** N-09/10/11/18; решения D-02/03/04.

Работа:

- Сохраняемый state machine старта, идемпотентная выдача шагов, безопасное продолжение после ошибки/загрузки.
- Происхождение → предыстория → обязательные Знамение/отдельный бонус по решению автора → сводка героя.
  В каждом шаге показывать конкретное изменение колоды, школ, ресурсов и Груза.
- Новый профиль/нет Нео/Пантеон off/старый Random-config — первые тестовые сценарии, не исключения «потом».
- Данные персонажа отдельно от эффектов их однократной выдачи. Учёт mastery по источникам:
  база/происхождение/предыстория/навык/очки характеристик/трактат/прочее.
- Respec возвращает только разрешённые траты и корректно перерассчитывает эффекты. Старые сейвы без истории трат

### S6. Баланс, симуляции и точечное расширение контента

**Предпосылки:** S1–S4 стабильны; UI позволяет правильно интерпретировать плейтест. Не балансировать поверх потерь карт.

#### S6.1 Инструменты и baseline

- Исправить допущения `burden_sim`: настоящий стартовый loadout, разные правила карт/реликвий, актуальная вместимость
  в момент подбора, 3/5 актов, сундук/мул/удаление, стратегия покупки. Не называть его боевым симулятором.
- Эвристический `balance_report` использовать как triage; вручную классифицировать условные/ресурсные карты.
- Лёгкий opt-in combat trace без личных данных: seed/версия/ход/колода/ресурсы/урон/выборы/источник награды,
  причины неиграбельности и отказа. Не писать гигабайты покадровых событий в обычном режиме.
- Создать ограниченный симулятор с явно описанными политиками и сравнить его с 10–20 эталонными реальными трассами.
  Не предполагать, что Python-копия и C# совпадают сами собой.

#### S6.2 Карты и архетипы

- Для каждого героя минимум 3 проверяемых направления; матрица ролей, common/uncommon/rare, enablers/payoffs,
  защита/добор/ресурсы/ответ на иммунитеты, доступ оружия и поддержки из реального пула.
- Латоносец: 1H/2H/щит/тяжёлая броня, кровотечение и Кличи; Безмолвная: скрытность/яд/охотник;
  Регент: эффективная мана/школы/связанное оружие/призывы/иллюзия. Не требовать, чтобы все ветки были одинаковы.
- Отдельно формы/Пути: когда получены, сколько боёв остаётся, вероятность увидеть поддержку и доля мёртвых предложений.
- Добавлять только закрывающие роль карты: 2–4 прототипа на выявленный пробел за итерацию. Для каждой — роль,
  цена энергии/◆/✦, редкость, upgrade, цель, текст, схема выпадения и тест эффекта. Никакого «340 → 500 для готовности».
- После каждой небольшой числовой итерации повторить те же seeds и сравнить; варианты hard gate тестировать отдельно.

#### S6.3 Враги, экономика и маршрут

- Сравнить обычных/элит/боссов каждого акта: burst/длительный бой/рой/броня/иммунитеты; минимальный набор контрмер
  достижим до встречи, интент не скрывает неожиданный летал.
- Боссы не должны проигрываться только одному узкому архетипу или требовать редкий предмет без альтернативы.
- Доверие/цены/заказы/ремесло/трактаты и Груз считать в общей экономике пяти актов; сравнить short run отдельно.
- Настраивать уровни «Реквием», когда baseline 0 принят; не исправлять неработающую механику одним множителем HP.

**Минимум измерений:** 1000+ симуляционных seeds на выбранную пару архетип/враг/акт/уровень после калибровки;
небольшая первая ручная серия 10 забегов/герой, затем расширение для спорных выводов.
Метрики: ходы/потеря HP/надрыв/остаток ◆✦/мёртвые руки/вес/заблокированные награды/собираемость ветки/причина смерти.
Показывать распределения и доверительные интервалы; 10 забегов недостаточно для уверенного заключения о winrate.

**Выход:** баланс-отчёт с данными, версиями модели/кода, известными смещениями и объяснением каждого изменения;
не заранее выдуманный «идеальный winrate».

### S7. Арт, анимации, звук и оптимизация

Подробные конкретные замечания и листы — в [арт-ревью](../review/art-audit-2026-11-18.md).

#### S7.1 Художественный pipeline

- Утвердить style board: 3–6 карт, один босс с фазой, несколько значков и реальный UI-экран.
- Сохранить фракционные палитры; добавить материал/глубину/разные силуэты и действие в карточной сцене.
- Порядок: важные UI/карта → стартовые/частые карты и формы → боссы/элиты → события/фоны → второстепенный контент.
- Карта рисуется от 32 px: уникальные силуэты лавок, без плотной мелкой штриховки; отдельная проверка на пергаменте/тёмном.
- Кукла: реальные хваты/pivot/слои, не просто ещё толще контур. Реликвии дорабатывать точечно — семейство уже сильнее остальных.
- Каждый ассет: исходник/лицензия/размеры/роль/принято на малом и большом размере/проверено в PCK.
  Ванильный fallback не удалять до готовности принятой замены.

#### S7.2 Motion и звук

- Полка Кличей: уход в слот/число ходов/возврат, не дым изгнания.
- Враги/формы: минимум idle/attack/hit/death/phase; переход фазы меняет читаемую позу/силуэт, не только яркость.
- Телеграфы до удара, урон в согласованный момент, короткая пауза обратной связи. Эффекты не растягивают обычный ход.
- Небольшие локальные ambient-движения фона; reduced motion и выключатели VFX/звука не меняют механику.
- Прослушать реальный микс, убрать лишние повторения/удвоения на multihit/repeat; существующая проверка WAV этого не делает.

#### S7.3 Измеренная оптимизация

- Baseline на фиксированной машине/разрешении: кадр p50/p95/p99, allocations/GC, живые UI-узлы,
  время открытия окна/генерации награды/загрузки акта, размер пакета и peak memory.
- Worst-case: 4–6 врагов с 10+ чертами, большая рука, открытые tooltips, 5 актов и возврат Камня.
- Сначала устранить подтверждённые hot spots: `NEnemyTraitChips.Collect/sort/hash/QueueRedraw` без изменения данных;
  остальным шкалам — event/invalidation и redraw только на изменении/активной анимации.
- Централизовать ресурсы/статы только с проверенной invalidation при gear/power/save/config-change.
- Проверить подписки/таймеры/статические кэши и 100 циклов открытия окон; не допустить регрессии корректности ради FPS.

**Выход:** `ART-01`, `UI-01…08`, `PERF-01…04`; отчёт до/после на одной конфигурации. Целевой бюджет UI и кадра
утвердить по baseline и целевому оборудованию, не обещать «60 FPS на любом ПК» по чтению кода.

### S8. Стабильная альфа и дальнейшая полировка

- Повтор всех P0/P1-сценариев, полная сборка именно выпускаемого commit, чистая установка DLL/PCK, список совместимости.
- Минимум 12 завершённых full-run маршрутов: 3 героя × 4 пары дверей; short run отдельно; формы/Пути и все боссы покрыты
  отдельными fixtures, если случайная выдача не позволяет пройти всё в этой выборке.
- Полный кооп на двух клиентах, возврат Камня/загрузка/отказ/выход, сверка значимых состояний.
- Старые сейвы/конфиги: миграция или явный отказ с объяснением и backup; никакого молчаливого уничтожения данных.
- Исходные `0/2` и `nope` закрыты воспроизведением и ретестом, а не отсутствием новых жалоб.
- Актуальный путеводитель/README, release notes, известные ограничения, способы прислать компактный диагностический отчёт.
- Релизный архив публикуется по существующим правилам проекта; игровые DLL, окружения и scratch-данные в Git не добавляются.

**Выход стабильной альфы:** нет P0/потерь данных, основные P1 закрыты, боевые/стартовые/маршрутные контракты приняты,
ключевой UI читаем, art placeholders не подменяют обещанный финальный контент. После этого — расширенная внешняя
проверка и художественная/балансная полировка до уровня замысла; «идеально» не достигается одной отметкой в таблице.

## 3. Исполнение первого пакета

Согласованный объём расширен автором до **всего блока 1 за текущий заход**. Это не только аудит/рекомендации:
исправления N-01…06, диагностическая часть N-07/08/15, сохранения/rollback и автоматические regressions внесены.
Подробное соответствие Б1.1–Б1.5 и оставшиеся границы автоматической проверки — в
[отчёте реализации](../review/stage-one-implementation-2026-11-18.md).

N-01 устранён в исходнике, но семантический full-mod build ещё не подтверждён. `0/2`/draw/`nope` инструментированы,
**не** объявлены воспроизведёнными/исправленными симптомами. Следующий шаг не требует ещё раз согласовывать начало Б1;
для запуска полного pipeline нужны легальные references и MegaDot. Финальный плейтест не переносится в середину работ.

## 4. Что нужно от игрового плейтеста

Это пакет для **финального** плейтеста, не запрос промежуточной игры и не блокировка реализации:

## 5. Как отслеживать продвижение

На каждую задачу: `ID → исходный commit → минимальный repro → решение → правка → auto-test → игровой тест → артефакт`.
Статусы: **запланировано / код готов / автоматически проверено / проверено в игре / визуально принято**.
Любой поздний фикс повторно открывает затронутые сценарии — как показал ref-capture после успешной сборки `ec598de`.

**Исторический результат исходного аудита `8000886`:** отчёт, матрица, просмотр арта и 22 проверки, без изменения
игровой механики в том аудиторском проходе. **Последующий реализационный проход — отдельный результат:**
[внесённый код блока 1 и его автоматические проверки](../review/stage-one-implementation-2026-11-18.md).
Статусы «проверено в игре» и «визуально принято» по-прежнему открыты.
